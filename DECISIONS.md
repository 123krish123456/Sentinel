# DECISIONS

- **D1 Log-diff edge cases:** if |Δln(parent)| < 1e-6 or any child is 0, use LMDI-style (logarithmic-mean) weights; if the parent change is "not material" (< min_rel_change) skip decomposition.
- **D2 Baseline MAD floor:** 4 same-weekday points are unstable; use sigma = max(1.4826·MAD, 0.05·|median|). "More conservative" baseline = the one giving the smaller |z|.
- **D3 Metric tree:** every rate has an explicit numerator/denominator in `config/metric_tree.yaml` so the product is exact; conversion_rate is split into 5 stage rates.
- **D4 Contribution chaining:** shares compose multiplicatively only within one decomposition; drill-down shares are fractions of the parent's Δ. Final report is capped at 100% and the remainder shown as unexplained. (Refine in M3.)
- **D6 Simulator size:** default 10k sessions/day; 50k–200k is opt-in.
- **D8 schema.yaml** is needed for M2, so it ships in M0 (`config/schema.yaml`).
- **D9 LLM cache key:** sha256(model, system, messages, tools, temperature); temperature 0.
- **D16 Scope cut:** FastAPI, Postgres and APScheduler are dropped from v1; CLI + Streamlit + cron.
- **D17 `Report.rejected`** uses a `RejectedHypothesis` model instead of a tuple.
- **D7 Late data / schema change:** modelled as per-day parquet files (`data/sim/<table>/<date>.parquet`). Late data = a partial file (`keep_fraction` of rows); schema change = renamed column in that day's file. No arrival-time column or row-count manifest; the DQ agent must infer from history.
- **D10 Scenario magnitudes:** effects are sized so the true revenue impact is >= ~6% (detection threshold 5%); S28 is a deliberate ~1% wobble that must not alert. Payment-failure scenarios use failure rates of 0.7-0.85 because android+upi is only ~10% of sessions.
- **D11 Ground truth:** each scenario day is re-generated without the scenario (same seed) to get `counterfactual_revenue`; `effect_revenue_delta` = true minus counterfactual. Per-segment contribution truth is not stored yet (add in M3 if needed).
- **D12 Effect model:** scenario `type` is a label; behaviour comes from params (`traffic_factor`, `atc_mult`, `checkout_mult`, `attempt_mult`, `amount_mult`, `failure_rate_to`). Data-issue types mutate the written tables. Sale days live in `settings.yaml` and are part of the baseline world, not a scenario.
- **D18 DQ row-count:** orders never checked against history (business scenarios legitimately move them). Sessions BLOCK if < 70% of trailing-14-day median; events checked as events-per-session ratio (same 70% BLOCK) so a traffic drop doesn't look like missing events. S17 (35% of sessions) and S18 (events at 60%) both hit this.
- **D19 DQ tracking checks are history-free invariants:** `orders == payment_success` (±2%) and "checkout_start sessions without add_to_cart ≤ 5%" -> WARN. Catches S13/S14 without confusing them with real funnel drops. Duplicates, null-rate rise (> 10pp vs median), new category values and schema diff also fire; `events.error_code` is excluded from category drift (new error codes are signal, not drift). `ts` outside the day is tolerated up to 1% (sessions spill past midnight).
- **D20 Detection:** `detect` checks every metric in `METRICS` against both baselines, uses the smaller |z|, and flags if |Δ| >= `min_rel_change` (5%) and |z| >= 2. Sigma floor is 3% of the median (tightens D2's 5%). Sale days (settings) are suppressed as known calendar events. Baseline days that are revenue/sessions outliers (prior incidents, late data) are dropped before averaging (`clean_baseline_days`); baselines are the *mean* of the clean daily cubes so segments stay additive. Known limit: daily revenue noise is ~6-8% (heavy-tailed AOV), so scenarios with a true effect below ~6% (S02, S07, S08, S12) are not reliably detected on revenue.
- **D21 Metric definitions (`analysis/metric_tree.py`):** sessions S, atc sessions A, checkout sessions C, attempt sessions P, orders O, revenue R. atc_rate=A/S, checkout_start_rate=C/A, payment_attempt_rate=P/C, payment_success_rate=O/P, conversion=O/S, aov=R/O; products telescope exactly. Session `payment_method` is the method of its payment_attempt ('none' otherwise), so it is only a valid dimension for revenue, orders, aov and payment_success_rate.
- **D22 Drill-down:** additive metrics use delta share; ratio metrics split each segment into rate_effect + mix_effect (exact, Simpson-safe; mix-dominated segments are terminal and not drilled further). A segment is a candidate if share >= 20%, volume >= 1%, baseline count >= 30, own move >= 5%, lift (share/volume) >= 1.5, and a sampling-noise z >= 3. Descend into a child only when it explains >= 70% of the node (more specific wins), otherwise branch to top-3. Same filter reached via several tree leaves has its contributions added (capped at 100%). The tree walk follows positive-share children only; leaves must have moved >= 3% and be |z| >= 2 vs their own history (heavy-tailed AOV otherwise soaks up the revenue change); if nothing in the tree is significant, the headline metric is drilled directly. Resolves HANDOFF §7 item 5.
- **D23 Baseline C result (M3 acceptance):** on the 14 single-cause scenarios the true filter set is in the top 3 for 10/14 (71%) exactly, 12/14 with partial overlap; misses are S08/S12 (true effect ~5% < noise), S05, S07. Two-cause scenarios (S23, S24) recover only the larger cause.
- **D24 LLM client (`llm/__init__.py`):** cache key = sha256(model, system, messages, tools, temperature, tool_choice) in `runs/llm_cache/`; the client returns plain dicts so any object with the same `create` can replace it (tests use a scripted fake). Token counts are tallied; cost is computed only if `pricing: {input_per_mtok, output_per_mtok}` is added to `settings.yaml` (left unset: I did not have verified pricing, see §7 item 13).
- **D25 Investigation agent:** the LLM gets the 7 PRD tools plus `segment_contribution` and a terminal `submit_hypotheses`; `find_causes` is deliberately withheld (it is Baseline C). `contribution_pct` is always recomputed in code as the segment's share of the revenue change (additive; overlapping hypotheses are scaled to <= 100%, remainder = unexplained). A hypothesis is dropped if it cites no known evidence id or contains a number not traceable to its cited evidence (`evidence/verifier.py`: rounding-aware, x100 for percentages, ignores dates/versions/ids); the model gets two chances to fix a bad submission. 25-call budget: once spent, only `submit_hypotheses` is offered (forced tool_choice).
- **D26 Critic checks (M5):** checks 1-5 (traffic, mix-shift, data-artifact, calendar, magnitude) run in pure Python before any LLM call; check 6 (alternatives + verdict assignment) uses the LLM with a `submit_verdicts` tool call (budget: 1 call). Confidence is computed in code: `0.5 × contribution_score + 0.3 × check_pass_rate + 0.2 × stat_strength`. Resolves HANDOFF §7 item 10.
- **D27 Eval matching (resolves HANDOFF §7 item 14):** a predicted filter set matches a true filter set iff it contains every (dimension, value) pair of the truth. Extra dimensions are allowed (more specific is fine); fewer dimensions or an empty set (global) never match. `overlap@3` (any shared pair) is reported alongside as a lenient view.
- **D28 Two-cause scoring (item 15):** acc@1/@3 count a hit on EITHER true cause; `both@3` requires both causes in the top 3.
- **D29 Baseline A sandbox (item 12):** LLM-written pandas runs in a subprocess with an allowlisted env (no API keys), temp cwd and a 40 s timeout, output truncated to 6 kB. No network or memory limit on Windows; use a container if untrusted input ever reaches it. Its tool outputs are stored as evidence so the same numeric verifier scores its hallucination rate.
- **D30 Contribution error:** truth is the injected effect (`effect_revenue_delta`) divided by the observed revenue move vs the detection baseline, clipped to 0-1; reported = summed contribution of the causes that match a true cause. Only scored when the system raised an anomaly. Per-segment truth is still not stored, so this is an approximation.
- **D31 Revise loop:** the Critic returns `revise` verdicts with hints; the orchestrator re-runs investigation with the hint (max `budgets.revise_loops`, 2), then re-reviews. A hypothesis still on `revise` afterwards is treated as rejected. A missing Critic verdict is `UNREVIEWED` with confidence capped at 0.3, never a silent accept.
- **D32 LLM provider:** `provider:` in settings.yaml selects an OpenAI-compatible endpoint (adapter in `llm/openai_compat.py`); without it the Anthropic API is used. Each eval system gets its own response cache so cache hits don't flatter latency or tokens.
- **D33 Olist adapter:** Olist has only completed orders (no sessions/funnel), so each order becomes one session with a full-funnel event trail. Revenue, orders, AOV, country, category and payment_method are real; traffic and conversion are degenerate by construction.
